## 6. 打印方案（沟通中，未定稿）

### 6.1 用户诉求

- 每个操作节点（收货 / 验收 / 上架 / 拣货 / **复核** / 发货 / 标签）可**配置**打印模板；
- **PDF 预览**；模板**内容可编辑**；能**调用打印机**打印；
- 支持**自动打印**（例：复核结束后自动触发打印）。

### 6.2 技术约束与关键事实

- 项目硬约束：**唯一 Python 依赖 Flask**，`web_app/` 零依赖原生 HTML/JS/CSS。
- 浏览器里的 `window.print()` **必然弹出系统打印对话框**，无法静默；真正的「自动打印」
  必须借助**本机打印代理**（浏览器 → 本机进程 → 打印机）。
- 环境现状：本机已装真实 Chrome（E2E 一直在用 `channel="chrome"`），
  因此 `chrome --headless --print-to-pdf --no-pdf-header-footer` 可**零新增 Python 依赖**生成 PDF。
- QZ Tray 是成熟的浏览器→本机打印桥（WebSocket，支持 PDF/PNG/HTML/ZPL/ESC-POS，
  Windows/macOS/Linux），但**静默打印需要证书签名**（免费版会有提示弹窗），
  且**每台机器只能跑一个实例**；引入它等于增加一次客户端安装与证书配置。

### 6.3 候选方案

| 方案 | PDF 生成 | 打印 / 自动打印 | 新增依赖 | 评价 |
|---|---|---|---|---|
| **A 浏览器原生**（推荐起步） | Chrome headless `--print-to-pdf`，或干脆直接打印 HTML | 节点完成后自动生成 PDF 并弹出打印预览/对话框，人工点确认 | 无 | 零安装、最快落地；「自动」＝自动出预览，**非静默** |
| **B 本地打印代理** | Chrome headless 出 PDF | QZ Tray（或自写极简本地 agent）接 WebSocket，按配置的打印机静默出纸 | 客户端装 QZ Tray + 签名证书 | 满足真正静默自动打印；多一层部署与运维 |
| **C 纯 Python 库** | ReportLab / WeasyPrint | 仍需 A 或 B 才能打印 | +1~N 个 Python 依赖，WeasyPrint 在 Windows 还需系统库 | 排版可控，但破坏「唯一依赖」且**不解决静默打印** |

### 6.4 推荐路径（分两步，先不锁死）

1. **先做 M41（方案 A 的超集）**：`print_template` 表存节点 / 模板 HTML 片段 / 字段映射 / 版本 /
   是否启用；管理页做「占位符 + 字段映射」式编辑 + 实时预览（iframe 直接预览 PDF）；
   后端用系统 Chrome headless 生成 PDF 落临时目录，前端 iframe 预览。
   **零新增 Python 依赖**，PDF、编辑、预览一次到位。
2. **M42 再接自动打印**：`print_job` 表 + 节点事件钩子（复核完成 / 验收入库 / 发货…）
   配置「节点 → 模板 → 打印机 → 触发方式」。默认行为＝自动生成 PDF 并弹出打印对话框；
   若用户确认需要**静默**，再引入 QZ Tray 或自写本地 agent，作为可选插件适配层，不改 M41 的模板层。

### 6.5 待用户确认（不提前拍板）

1. 「自动打印」是否必须**完全静默**（需装本机代理/证书），还是「自动弹出已生成 PDF 的打印预览、人工确认」即可？
2. PDF 生成用「系统 Chrome headless（零 Python 依赖，但要求部署机有 Chrome）」，还是允许加一个纯 Python 库？
3. 「内容可编辑」指的是**模板本身**可编辑（占位符/字段映射），还是**打印前可临时改单据内容**（数量 / 备注 / 收货人）？两者可都做，但成本不同。
4. 模板编辑要做到「占位符 + 字段映射」够用，还是必须**可视化拖拽排版**？
5. 自动触发的**首批节点清单**（用户已举例「复核结束」），是否先按「验收 / 复核 / 发货」三个节点起？
